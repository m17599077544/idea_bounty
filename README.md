# Idea Bounty

AI 驱动的商业点子悬赏平台。用户提交一个真实痛点或商业点子，系统会评估它的商业价值、判断是否与历史点子语义重复，并给出对应的红包金额和解释。

## 1. 快速运行

### 环境要求

- Node.js 18+
- npm
- 一个可用的 DeepSeek API Key

### 安装与配置

在项目根目录执行：

```powershell
npm install
Copy-Item .env.example .env
```

编辑 `.env`：

```env
OPENAI_API_KEY=你的 DeepSeek API Key
```

虽然变量名沿用了 OpenAI SDK 的命名，实际请求地址和模型配置在 `src/lib/ai.ts` 中指向 DeepSeek。

### 启动开发服务器

```powershell
npm run dev
```

打开：

- 用户前台：http://localhost:3000
- 管理后台：http://localhost:3000/admin

### 生产模式

```powershell
npm run build
npm start
```

### 手机或其他网络访问

同一 Wi-Fi 下，使用电脑局域网 IPv4 地址访问：

```text
http://电脑局域网IP:3000
```

查看地址：

```powershell
ipconfig
```

临时分享给其他网络，可以安装 Cloudflare Tunnel 后执行：

```powershell
cloudflared tunnel --protocol quic --url http://localhost:3000
```

使用命令输出的 `https://*.trycloudflare.com` 地址访问。Next.js 和 cloudflared 两个窗口都必须保持运行。

## 2. 核心功能

### 用户前台

- 痛点 / 点子描述为必填项。
- 标题可选，不填写时自动从描述生成。
- 实施方案、分类、昵称为可选项。
- 提交后显示红包金额、三项评分和 AI 评语。
- 发现相似历史点子时，明确显示“已有人提过类似点子”或“发现疑似类似点子”。

### AI 评估

评分维度为 0～10 分：

- 需求广度：有多少人受到影响。
- 付费意愿：用户是否愿意为解决方案付费。
- 可行性：方案是否现实、是否具备差异化空间。

基础红包根据三项评分计算，重复点子会覆盖基础红包：

- 语义重复：红包大幅减少，通常为 0。
- 疑似重复：保留最高约 1 元的鼓励金。
- 全新且有价值：按评分发放更高红包。

### 后台管理

访问 `/admin` 可查看：

- 全部提交记录。
- AI 三项评分、Boss 红包和最终红包金额。
- 原创、疑似重复、重复判定。
- 语义相似度和匹配的历史点子。
- 提交总数、红包总额、原创数量、重复数量、待审核数量、Boss 数量、平均分。

管理员可以：

- 手动调整红包金额。
- 通过记录。
- 驳回记录。

## 4. 查重方案

查重使用 LLM 做语义判断，不比较简单的字符串相等。模型会先抽取并比较：

- 核心痛点。
- 受影响的人群。
- 想改善的结果。

例如“每个月还没到月底钱就花光了”和“我总是控制不住乱花钱存不下来”，即使没有相同句子，也会因为核心问题都是个人消费管理困难而被判定为重复。

模型会选择最相似的一条历史记录，并返回语义相似度、判定级别、历史标题和大白话原因。当前实现将全部历史点子摘要放进查重 Prompt，适合 MVP 和小数据量，不适合无限增长的数据规模。

## 5. 防止用户忽悠 AI

用户可以把点子写得非常夸张，因此评分流程不会直接相信营销话术。AI 评分 Prompt 要求：

1. 先从描述中提取可验证的客观事实。
2. 忽略“市场巨大”“人人需要”“一定成功”等自我宣传。
3. 基于事实评估需求广度、付费意愿和可行性。
4. Boss 红包额外检查市场、政策、社会价值、趋势、乡村振兴和核心价值观条件。

取舍是：这种方式能减少明显的夸大描述，但仍然不是事实核验系统。模型可能误判，管理员可以在后台调整或驳回结果。

## 6. AI 协作复盘 Writeup

### 使用了什么 AI 工具

开发过程中使用 Codex 作为代码代理，主要用于：

- 阅读项目结构和现有实现。
- 按 Next.js 16 的本地文档检查 App Router、Route Handler 和异步 `params` 用法。
- 设计和实现表单、结果卡片、后台表格和 API 流程。
- 检查评分、查重、数据库和 API 的边界问题。
- 运行 `npm run build`、`npm run lint` 并根据输出修复问题。
- 生成用户说明、部署说明和本 README。

DeepSeek API 则作为产品运行时的评估模型，用于查重、客观事实提取、商业评分和 Boss 条件判断。

### AI 帮上忙的地方

- 快速搭建了从前端表单到 API、AI、SQLite 的完整闭环。
- 发现了“痛点描述被错误设为可选”的产品问题，并调整为真正的核心必填项。
- 将查重从字面匹配要求提升为核心痛点和目标结果的语义比较。
- 发现并修复了后台平均分被额外除以 3 的统计错误。
- 识别出后台操作接口缺少鉴权、没有限流等上线风险。

### AI 帮倒忙或需要人工判断的地方

- 早期代码和文档同时出现 OpenAI、DeepSeek、Embedding 等不一致描述，需要人工核对实际配置。
- LLM 很容易把“行业相同”误判为“问题相同”，所以查重 Prompt 必须加入反例和明确分级规则。
- AI 生成的评分不代表真实市场验证，不能把红包金额当成投资或商业结论。
- React 19 的 lint 规则与旧式 `useEffect` 写法存在冲突，构建可以通过但质量门禁仍未完全通过。

## 7. 如果再开发一周

优先级如下：

1. 增加管理员登录、服务端鉴权和操作审计日志。
2. 将长时间 AI 评估改为异步任务，避免请求超时和重复提交。
3. 用 Embedding + 候选召回替代把全部历史记录塞进 Prompt，降低成本和上下文膨胀风险。
4. 增加限流、验证码、请求体限制和失败重试。
5. 增加自动化测试，覆盖查重分级、红包计算、API 校验和数据库操作。
6. 将 SQLite 替换为适合线上多实例部署的数据库，并增加数据库迁移。
7. 增加真实用户反馈，用人工标注数据评估查重准确率和评分一致性。

## 8. 已知问题和未完成部分

- 当前没有真正的用户登录、管理员登录和权限模型。
- 红包只是展示和数据库记录，没有真实支付。
- 查重仍依赖 LLM，历史记录很多时 Prompt 会变大，成本和延迟会上升。
- 数据库是本地 SQLite，不适合直接部署到无持久磁盘或多实例环境。
- 当前没有 Embedding 向量库，数据库中的 `embedding` 字段暂未实际使用。
- 没有真实市场数据、用户行为数据或人工标注集来验证 AI 评分。
- `npm run build` 可以通过，但 `npm run lint` 仍有项目原有的 React effect 和链接规范问题。
- Cloudflare Quick Tunnel 仅用于临时演示，地址会变化，不是正式生产部署方案。
